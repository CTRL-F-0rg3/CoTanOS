Introduction

This document describes a complete 64-bit RISC-V processor design written in Verilog HDL, along with its full verification environment in assembly. The core implements the base RV64I instruction set, the multiply/divide extension M, and the Zicsr extension (CSR + traps). It is built as a 5-stage pipeline with data forwarding, load-use hazard detection, and software-interrupt handling.

This project is a starting point for learning the entire silicon design process — from ISA specification, through RTL, simulation, and verification, to tape-out preparation. It is also a foundation for a custom operating system: the core can be extended with additional features (UART, timers, MMU) towards compatibility with the QEMU virt platform.

How Silicon Is Made — Project Context

Designing a processor is a multi-month process broken into several phases. Understanding them is crucial, because RTL and simulation are only about 20% of the total work. Below is the roadmap from idea to physical chip.

Phase 1 — Specification and Reference Model

Before the first line of RTL is written, an executable specification is created — an ISA model (Instruction Set Simulator, ISS) written in C, Rust, or Python. This model is the "golden reference": whatever the RTL does must produce an identical result. The standard in the RISC-V world is Spike — the official ISS.

Phase 2 — RTL Design

RTL (Register Transfer Level) describes hardware in an HDL (Verilog, SystemVerilog, Chisel, VHDL). Our core is at this stage. RTL defines how signals propagate between registers in each clock cycle.

Phase 3 — Functional Verification

60–70% of the entire project time is verification. It proves that the RTL matches the specification. Methods:

  • Directed tests — hand-written assembly programs (our .S)
  • Constrained-random — random instruction sequence generators (riscv-dv)
  • Formal verification — mathematical proof of properties (SymbiYosys)
  • Compliance tests — official ISA tests (riscv-arch-test)
  • Golden trace — comparison of execution trace with Spike or QEMU

Phase 4 — Synthesis and Physical Analysis

RTL is translated into logic gates (synthesis, e.g. Yosys, Design Compiler), then into a physical layout (place & route). The result is a GDSII file — ready to be sent to the fab.

Phase 5 — Tape-out

Tape-out is the moment the design (GDSII) is sent to the foundry (TSMC, GlobalFoundries, Intel Foundry). Cost: from hundreds of thousands to tens of millions of dollars — depending on the lithography. One bug = months of waiting and lost money, which is why verification matters so much.

Where we are in this process We are in Phase 2 and 3 — we have working RTL and a basic set of tests. Next steps: extended verification (formal, golden trace), peripheral integration (UART, CLINT), QEMU integration.

RISC-V in a Nutshell

RISC-V is an open Instruction Set Architecture (ISA) designed at UC Berkeley in 2010. Unlike ARM and x86 it is completely free and open — anyone can design and manufacture their own processor without licensing fees. It is modular: a base set plus optional extensions.

Our configuration

The implemented core supports RV64IM_Zicsr. This is the minimal set that allows bare-metal programs to run, but not a full operating system (missing MMU, S-mode, external interrupts).

RISC philosophy

  • Fixed instruction length — 32 bits (4 bytes), simple fetch
  • Load/store architecture — ALU works only on registers, not memory
  • 32 general-purpose registers + x0 hardwired to zero
  • No flags — comparisons via dedicated instructions (slt, beq)
  • PC-relative addressing — code is position independent

RTL Modules

ALU — Arithmetic Logic Unit

The ALU (rv64i_pipe_alu) is a combinational block that computes the result of an operation in the EX stage. It handles 29 operations: base RV64I ALU, the M extension (mul/div), and 32-bit sign-extending variants (ADDW/SUBW/SLLW/...).

Operation list

CodeOperationDescription
0-9ADD, SUB, SLL, SLT, SLTU, XOR, SRL, SRA, OR, ANDBase RV64I
10PASSPass-through B (for LUI)
11-15ADDW, SUBW, SLLW, SRLW, SRAW32-bit + sign-extend
16-19MUL, MULH, MULHSU, MULHUMultiply (low/high, signed/unsigned)
20-23DIV, DIVU, REM, REMUDivide (signed/unsigned, quotient/remainder)
24-28MULW, DIVW, DIVUW, REMW, REMUWW-variants (32-bit + sign-extend)

Key snippet — signed division

wire signed [63:0] a_s = a;
wire signed [63:0] b_s = b;

// Ternary result type = common type of both branches.
// If any branch is unsigned, the whole expression becomes unsigned,
// and Verilator casts a_s/b_s to unsigned before dividing.
wire signed [63:0] div_q_s =
    (b_s == 64'sd0) ? -64'sd1 :
    (a_s == 64'sh8000000000000000 && b_s == -64'sd1) ? 64'sh8000000000000000 :
    a_s / b_s;
Signed/unsigned pitfall If we had written ? 64'hFFFFFFFFFFFFFFFF : a_s / b_s, the whole ternary expression would become unsigned per IEEE 1800, and Verilator would cast the operands to unsigned before dividing. This is a classic RTL bug — one that formal equivalence checking catches.

Register File

32 registers, 64 bits each. Register x0 is hardwired to zero — reads always return 0, writes are ignored. Key feature: write-first bypass, allowing the register file to return a newly-written value in the same cycle it's written. 

module rv64i_pipe_regfile (
    input wire clk, rst,
    input wire [4:0] rs1, rs2, rd,
    input wire [63:0] wdata,
    input wire we,
    output wire [63:0] rdata1, rdata2
);
    reg [63:0] regs [0:31];
    integer i;

    always @(posedge clk) begin
        if (rst) for (i=0; i<32; i=i+1) regs[i] <= 64'd0;
        else if (we && rd != 5'd0) regs[rd] <= wdata;
    end

    // Write-first bypass: ID read in same cycle as WB write
    // must see the new value. Covers 3-instruction gaps that
    // 2-level EX/MEM + MEM/WB forwarding cannot reach.
    assign rdata1 = (rs1 == 5'd0) ? 64'd0 :
                    (we && rd == rs1) ? wdata : regs[rs1];
    assign rdata2 = (rs2 == 5'd0) ? 64'd0 :
                    (we && rd == rs2) ? wdata : regs[rs2];
endmodule
Why write-first? Without this bypass, the sequence divuw → lui → addi → bne (3 instructions between producer and consumer) gives a wrong result. Standard EX/MEM + MEM/WB forwarding covers gaps of 1 and 2 instructions, but not 3. A write-first regfile costs no extra gates — just a mux on the output.

Immediate formation

RISC-V has 5 different immediate formats. Each must be sign-extended to XLEN. The decoder does this combinationally: 

// I-type: instr[31:20] sign-extended
wire [63:0] imm_i = {{52{instr[31]}}, instr[31:20]};

// S-type: instr[31:25] || instr[11:7]
wire [63:0] imm_s = {{52{instr[31]}}, instr[31:25], instr[11:7]};

// B-type: {instr[31], instr[7], instr[30:25], instr[11:8], 0}
wire [63:0] imm_b = {{51{instr[31]}}, instr[31], instr[7],
                     instr[30:25], instr[11:8], 1'b0};

// J-type: {instr[31], instr[19:12], instr[20], instr[30:21], 0}
wire [63:0] imm_j = {{43{instr[31]}}, instr[31], instr[19:12],
                     instr[20], instr[30:21], 1'b0};

// U-type: instr[31:12] << 12, sign-extended
wire [63:0] imm_u = {{32{instr[31]}}, instr[31:12], 12'b0};
LUI pitfall in RV64 LUI in RV32 does imm << 12 into 32 bits. In RV64 the result is sign-extended to 64 bits — so lui x4, 0x80001 gives 0xFFFFFFFF80001000, not 0x0000000080001000. This is why our tests use auipc + addi instead of lui to load addresses above 0x8000_0000.

Pipeline Core

The core's top level. It contains 5 stages, 4 pipeline registers (IF/ID, ID/EX, EX/MEM, MEM/WB), the forwarding unit, and the hazard detector. Full structure below. 

module rv64i_pipe_core (
    input  wire        clk, rst,
    output wire [63:0] imem_addr,
    input  wire [31:0] imem_data,
    output wire [63:0] dmem_addr, dmem_wdata,
    output wire        dmem_we, dmem_re,
    output wire [1:0]  dmem_size,
    input  wire [63:0] dmem_rdata,
    output reg         halted,
    output wire [63:0] dbg_pc
);
    // IF stage
    reg  [63:0] pc;
    wire [31:0] if_instr = imem_data;
    assign imem_addr = pc;

    // IF/ID register
    reg [63:0] ifid_pc;
    reg [31:0] ifid_instr;
    reg        ifid_valid;

    // ID stage → decoder instance
    // EX stage → ALU + forwarding + branch resolution
    // MEM stage → memory access
    // WB stage → writeback to regfile
    // ...
endmodule

Memory

The rv64i_mem module emulates a Harvard memory: separate instruction (32-bit words) and data (64-bit words) ports. It also detects writes to tohost at 0x8000_1000 — the standard testbench communication mechanism (the riscv-tests protocol). 

module rv64i_mem #(
    parameter MEM_WORDS = 32768,
    parameter BASE      = 64'h0000_0000_8000_0000
)(
    // instruction port
    input  wire [63:0] iaddr,
    output wire [31:0] idata,
    // data port
    input  wire [63:0] daddr, dwdata,
    input  wire        dwe, dre,
    input  wire [1:0]  dsize,
    output wire [63:0] drdata,
    // tohost interface
    output reg         tohost_we,
    output reg  [63:0] tohost_data
);
    reg [31:0] imem [0:MEM_WORDS-1];
    reg [63:0] dmem [0:MEM_WORDS-1];
    reg [1023:0] hexpath;

    initial begin
        if ($value$plusargs("HEX=%s", hexpath))
            $readmemh(hexpath, imem);
    end
    // ...
endmodule
tohost convention Program writes 1 to 0x8000_1000 = PASS. Value > 1 = number of the failing test. This is the standard used by riscv-tests and riscv-arch-test — if our core supports it, it will be compatible with the official test suites.

Pipeline In Depth

The classic 5-stage RISC pipeline. Each stage does one thing and passes its result to the next through a pipeline register. In one clock cycle, 5 instructions are at different stages of completion.

1IFFetch — get instruction from I-mem
→
2IDDecode — decode, read registers
→
3EXExecute — ALU, branch, CSR
→
4MEMMemory — load/store
→
5WBWriteback — write to regfile

IF — Instruction Fetch

The IF stage fetches a 32-bit instruction from memory at address pc. In the same cycle it computes pc + 4 as the default next PC. 

reg  [63:0] pc;
wire [31:0] if_instr = imem_data;
assign imem_addr = pc;

always @(posedge clk) begin
    if (ex_redirect)       pc <= ex_redirect_target;
    else if (!stall)        pc <= pc + 64'd4;
end

Two things can change PC:

  • Redirect — branch taken, JAL/JALR, trap, mret
  • Stall — load-use hazard, PC freezes

ID — Instruction Decode

The decoder translates the 32-bit instruction into control signals. At the same time, the register file reads rs1 and rs2. Results are latched into the IF/ID → ID/EX register. 

always @(posedge clk) begin
    if (flush || stall) begin
        // bubble — clear all control signals
        idex_reg_we <= 1'b0;
        idex_mem_re <= 1'b0;
        idex_mem_we <= 1'b0;
        // ...
    end else begin
        idex_pc      <= ifid_pc;
        idex_rs1_val <= id_rs1_val;
        idex_rs2_val <= id_rs2_val;
        idex_imm     <= id_imm;
        idex_alu_op  <= id_alu_op;
        // ...
    end
end

EX — Execute

The EX stage does the most work: ALU, branch resolution, CSR access, trap detection. Forwarding also happens here — data from EX/MEM and MEM/WB can be used instead of reading from the regfile.

Forwarding (priority EX/MEM > MEM/WB > regfile)

wire fwd_a_exmem = exmem_reg_we && (exmem_rd != 5'd0) && (exmem_rd == idex_rs1);
wire fwd_b_exmem = exmem_reg_we && (exmem_rd != 5'd0) && (exmem_rd == idex_rs2);
wire fwd_a_memwb = memwb_reg_we && (memwb_rd != 5'd0) && (memwb_rd == idex_rs1) && !fwd_a_exmem;
wire fwd_b_memwb = memwb_reg_we && (memwb_rd != 5'd0) && (memwb_rd == idex_rs2) && !fwd_b_exmem;

wire [63:0] ex_rs1 = fwd_a_exmem ? exmem_alu_y : fwd_a_memwb ? wb_wdata : idex_rs1_val;
wire [63:0] ex_rs2 = fwd_b_exmem ? exmem_alu_y : fwd_b_memwb ? wb_wdata : idex_rs2_val;

Branch resolution

always @(*) begin
    case (idex_branch_op)
        3'b001: ex_branch_taken = (ex_rs1 == ex_rs2);              // BEQ
        3'b010: ex_branch_taken = (ex_rs1 != ex_rs2);              // BNE
        3'b011: ex_branch_taken = ($signed(ex_rs1) < $signed(ex_rs2)); // BLT
        3'b100: ex_branch_taken = ($signed(ex_rs1) >= $signed(ex_rs2)); // BGE
        3'b101: ex_branch_taken = (ex_rs1 < ex_rs2);              // BLTU
        3'b110: ex_branch_taken = (ex_rs1 >= ex_rs2);             // BGEU
        default:ex_branch_taken = 1'b0;
    endcase
end
Branch penalty = 2 cycles Resolving the branch in EX means the 2 instructions fetched after the branch (in IF and ID) are wrong if the branch is taken — they must be flushed. This is the cost of 2 cycles per taken branch. Production cores resolve the branch earlier (in ID) or use branch prediction to reduce this cost.

MEM — Memory

Data memory access. Only load/store instructions do anything here — for the others, it just "passes through" the ALU result. 

assign dmem_addr  = exmem_alu_y;
assign dmem_wdata = exmem_rs2_val;
assign dmem_we    = exmem_mem_we;
assign dmem_re    = exmem_mem_re;
assign dmem_size  = exmem_mem_size;

WB — Writeback

Write the result to the register file. The result can come from three sources:

  • ALU — for arithmetic operations
  • Memory — for load (with sign/zero extension)
  • CSR — for CSR instructions
assign wb_wdata = memwb_is_csr ? memwb_csr_rdata :
                  memwb_mem_re ? wb_load_ext : memwb_alu_y;
assign wb_we    = memwb_reg_we;
assign wb_rd    = memwb_rd;

Hazards and Forwarding

RAW (Read After Write) — data hazard

The most common hazard: an instruction wants to read a register that has not yet been written by a previous instruction (because it is in EX/MEM, not WB). 

# RAW example
add  x1, x2, x3   # x1 ready after WB
add  x4, x1, x5   # but needed already in EX → forwarding!

Solution: forwarding (data bypass). The result from EX/MEM or MEM/WB is fed directly to the ALU input, instead of waiting for WB.

Load-use hazard

Special case: a load instruction has its result only after MEM, so even forwarding is not enough. The pipeline must stall for 1 cycle (insert a bubble). 

# Load-use — requires stall
ld   x1, 0(x2)     # load
add  x3, x1, x4    # uses x1 — must wait 1 cycle
wire load_use_hazard =
    idex_mem_re && (idex_rd != 5'd0) && ifid_valid &&
    ((idex_rd == id_rs1) || (idex_rd == id_rs2));

wire stall = load_use_hazard;
Stall = bubble in EX When stall=1, the ID/EX register writes a bubble (all control signals to 0). This guarantees the EX stage executes a NOP instead of re-executing the same instruction.

Control hazard

Branch resolved in EX, so the instructions fetched in IF and ID (after the branch) are wrong if the branch is taken. They must be flushed — zero ifid_valid and the control signals in ID/EX. 

wire ex_redirect = ex_trap_take || ex_mret_take
                   || idex_is_jump || (idex_is_branch && ex_branch_taken);
wire flush = ex_redirect;

Write-first regfile — 3-instr gap

Standard forwarding covers gaps of 1 and 2 instructions. A 3-instruction gap (e.g. divuw → lui → addi → bne) requires a write-first regfile or a third level of forwarding. 

assign rdata1 = (rs1 == 5'd0) ? 64'd0 :
                (we && rd == rs1) ? wdata : regs[rs1];

CSR and Traps — in Practice

RISC-V's trap handling is unified — all exceptions go through the same mechanism:

  1. Processor writes mepc ← current PC
  2. Writes mcause ← cause code
  3. Writes mtval ← additional info (e.g. instruction code)
  4. Sets mstatus.MPIE ← mstatus.MIE, MIE ← 0
  5. Jumps to mtvec (handler address)

Return via mret:

  1. mstatus.MIE ← mstatus.MPIE
  2. mstatus.MPIE ← 1
  3. PC ← mepc

Example — ecall handler

handler:
    addi a0, a0, 1        # increment counter
    csrr t0, mepc
    addi t0, t0, 4        # skip ecall (PC += 4)
    csrw mepc, t0
    mret                  # return
Test trap.S — PASS The test verifies: CSR read/write round-trip (mscratch), ecall → handler → mret, and check that mcause = 11 after return. All conditions passed on RTL.

-T link.ldLinker script with _start @ 0x8000_0000
Pitfall — la generates GOT access Without -fno-pic -mcmodel=medany + .hidden tohost, the pseudo-instruction la t0, tohost generates a GOT access (auipc + ld), and the GOT in a non-relocated binary is garbage. This leads to a silent timeout. We saw this — t0 got 0 instead of 0x80001000.

bin → hex conversion (byte-swap)

RISC-V memory is little-endian, but $readmemh reads 32-bit words. Must convert 13 05 50 00 (4 bytes) into 00500513 (one 32-bit word). 

python3 - "$BASE.bin" > "$BASE.hex" <<'PY'
import sys
d = open(sys.argv[1],'rb').read()
while len(d) % 4: d += b'\x00'
for i in range(0, len(d), 4):
    print(f'{int.from_bytes(d[i:i+4], "little"):08x}')
PY

Target architecture

The goal is a core compatible with the QEMU -M virt platform, allowing the same OS to run on:

  • QEMU — fast prototyping (on x86_64)
  • Own RTL — Verilator simulation
  • FPGA — real hardware (Artix-7 / ECP5)
  • Silicon — if it ever goes to tape-out

Key: identical peripheral addresses. UART @ 0x1000_0000, CLINT @ 0x0200_0000, PLIC @ 0x0C00_0000 — exactly like QEMU virt. Then uart_putc in the OS works unchanged on all platforms.

Golden trace — the foundation of verification

# 1. Run on QEMU, save trace
qemu-system-riscv64 -M virt -bios none -kernel test.elf \
    -d in_asm,cpu -D qemu.trace -nographic

# 2. Run on RTL, save trace (extend tb with $fdisplay)
./obj_dir/Vtb_rv64i_soc +HEX=test.hex > rtl.trace

# 3. Diff
python3 scripts/diff_qemu.py qemu.trace rtl.trace
