Wprowadzenie

Ten dokument opisuje kompletny projekt procesora RISC-V 64-bitowego napisany w Verilog HDL, wraz z całym otoczeniem weryfikacyjnym w asemblerze. Rdzeń implementuje bazowy zestaw RV64I, rozszerzenie mnożenia/dzielenia M oraz rozszerzenie Zicsr (CSR + trapy). Został zaprojektowany jako 5-stopniowy potok z forwardingiem danych, detekcją hazardów load-use i obsługą przerwań programowych.

Projekt jest punktem wyjścia do nauki całego procesu projektowania krzemu — od specyfikacji ISA, przez RTL, symulację, weryfikację, aż po przygotowanie do tape-out'u. Jest również bazą pod własny system operacyjny: rdzeń można rozszerzać o kolejne rozszerzenia (UART, timery, MMU) w kierunku zgodności z platformą QEMU virt.

Jak powstaje krzem — kontekst projektu

Zaprojektowanie procesora to wielomiesięczny proces podzielony na kilka faz. Zrozumienie ich jest kluczowe, bo RTL i symulacja to zaledwie 20% całej pracy. Poniżej mapa drogowa od pomysłu do fizycznego układu.

Faza 1 — Specyfikacja i model referencyjny

Zanim powstanie pierwsza linia RTL, powstaje wykonywalna specyfikacja — model ISA (Instruction Set Simulator, ISS) napisany np. w C, Rust lub Pythonie. Ten model jest "złotym odniesieniem": cokolwiek zrobi RTL, musi dać identyczny wynik. Standardem w świecie RISC-V jest Spike — oficjalny symulator ISS.

Faza 2 — Projekt RTL

RTL (Register Transfer Level) to opis sprzętu w języku HDL (Verilog, SystemVerilog, Chisel, VHDL). Nasz rdzeń jest w tej fazie. RTL definiuje, jak sygnały propagują się między rejestrami w każdym cyklu zegara.

Faza 3 — Weryfikacja funkcjonalna

60–70% całego czasu projektu to weryfikacja. Polega na dowodzeniu, że RTL jest zgodny ze specyfikacją. Metody:

  • Directed tests — ręcznie pisane programy w asemblerze (nasze .S)
  • Constrained-random — generator losowych sekwencji instrukcji (riscv-dv)
  • Formal verification — matematyczny dowód właściwości (SymbiYosys)
  • Compliance tests — oficjalne testy ISA (riscv-arch-test)
  • Golden trace — porównanie śladu wykonania z Spike lub QEMU

Faza 4 — Synteza i analiza fizyczna

RTL jest tłumaczony na bramki logiczne (synteza, np. Yosys, Design Compiler), potem na fizyczny layout (place & route). Wynikiem jest plik GDSII — gotowy do wysłania do fabryki.

Faza 5 — Tape-out

Tape-out to moment, w którym projekt (GDSII) jest wysyłany do fabryki (TSMC, GlobalFoundries, Intel Foundry). Koszt: od kilkuset tysięcy do kilkudziesięciu milionów dolarów — zależnie od litografii. Jeden błąd = miesiące oczekiwania i strata pieniędzy, dlatego weryfikacja jest tak ważna.

Gdzie jesteśmy w tym procesie Jesteśmy w fazie 2 i 3 — mamy działający RTL i podstawowy zestaw testów. Kolejne kroki: rozszerzenie weryfikacji (formal, golden trace), dodanie peryferiów (UART, CLINT), integracja z QEMU.

RISC-V w pigułce

RISC-V to otwarty zestaw instrukcji (ISA) zaprojektowany na UC Berkeley w 2010 roku. W przeciwieństwie do ARM i x86 jest całkowicie darmowy i otwarty — każdy może zaprojektować i wyprodukować własny procesor bez opłat licencyjnych. Jest modularny: bazowy zestaw + opcjonalne rozszerzenia.

Nasz zestaw

Zaimplementowany rdzeń obsługuje: RV64IM_Zicsr. To minimalny zestaw, który pozwala uruchomić bare-metalowe programy, ale nie pełny system operacyjny (brakuje MMU, S-mode, przerwań zewnętrznych).

Filozofia RISC

  • Stała długość instrukcji — 32 bity (4 bajty), prosty fetch
  • Load/store architecture — ALU operuje tylko na rejestrach, nie na pamięci
  • 32 rejestry uniwersalne + x0 hardwired do zera
  • Brak flag — porównania robi się przez dedykowane instrukcje (slt, beq)
  • Adresowanie PC-relative — kod jest pozycyjnie niezależny

Moduły RTL

ALU — jednostka arytmetyczno-logiczna

ALU (rv64i_pipe_alu) to kombinator obliczający wynik operacji w stopniu EX. Obsługuje 29 operacji: bazowe ALU RV64I, rozszerzenie M (mul/div) oraz operacje 32-bitowe z sign-extension (ADDW/SUBW/SLLW/...).

Kluczowy fragment — signed division

wire signed [63:0] a_s = a;
wire signed [63:0] b_s = b;

// Ternary result type = common type of both branches.
// If any branch is unsigned, the whole expression becomes unsigned,
// and Verilator casts a_s/b_s to unsigned before dividing.
wire signed [63:0] div_q_s =
    (b_s == 64'sd0) ? -64'sd1 :
    (a_s == 64'sh8000000000000000 && b_s == -64'sd1) ? 64'sh8000000000000000 :
    a_s / b_s;
Pułapka signed/unsigned Gdybyśmy napisali ? 64'hFFFFFFFFFFFFFFFF : a_s / b_s, cała wyrażenie ternary stałoby się unsigned wg IEEE 1800, i Verilator rzutowałby operandy na unsigned przed dzieleniem. To klasyczny bug RTL — jeden z tych, które wyłapuje formal equivalence checking.

Register File

32 rejestry 64-bitowe. Rejestr x0 jest hardwired do zera — odczyt zawsze zwraca 0, zapis jest ignorowany. Kluczowy feature: write-first bypass, który pozwala odczytać nową wartość w tym samym cyklu, w którym jest zapisywana. 

module rv64i_pipe_regfile (
    input wire clk, rst,
    input wire [4:0] rs1, rs2, rd,
    input wire [63:0] wdata,
    input wire we,
    output wire [63:0] rdata1, rdata2
);
    reg [63:0] regs [0:31];
    integer i;

    always @(posedge clk) begin
        if (rst) for (i=0; i<32; i=i+1) regs[i] <= 64'd0;
        else if (we && rd != 5'd0) regs[rd] <= wdata;
    end

    // Write-first bypass: ID read in same cycle as WB write
    // must see the new value. Covers 3-instruction gaps that
    // 2-level EX/MEM + MEM/WB forwarding cannot reach.
    assign rdata1 = (rs1 == 5'd0) ? 64'd0 :
                    (we && rd == rs1) ? wdata : regs[rs1];
    assign rdata2 = (rs2 == 5'd0) ? 64'd0 :
                    (we && rd == rs2) ? wdata : regs[rs2];
endmodule
Dlaczego write-first? Bez tego bypassu, sekwencja divuw → lui → addi → bne (3 instrukcje między producentem a konsumentem) daje zły wynik. Standardowe forwarding EX/MEM + MEM/WB pokrywa luki 1 i 2 instrukcji, ale nie 3. Write-first regfile nie kosztuje dodatkowych bramek — po prostu multiplekser na wyjściu.

Formowanie immediate'ów

RISC-V ma 5 różnych formatów immediate. Każdy trzeba sign-extendować do XLEN. Dekoder robi to kombinatorowo: 

// I-type: instr[31:20] sign-extended
wire [63:0] imm_i = {{52{instr[31]}}, instr[31:20]};

// S-type: instr[31:25] || instr[11:7]
wire [63:0] imm_s = {{52{instr[31]}}, instr[31:25], instr[11:7]};

// B-type: {instr[31], instr[7], instr[30:25], instr[11:8], 0}
wire [63:0] imm_b = {{51{instr[31]}}, instr[31], instr[7],
                     instr[30:25], instr[11:8], 1'b0};

// J-type: {instr[31], instr[19:12], instr[20], instr[30:21], 0}
wire [63:0] imm_j = {{43{instr[31]}}, instr[31], instr[19:12],
                     instr[20], instr[30:21], 1'b0};

// U-type: instr[31:12] << 12, sign-extended
wire [63:0] imm_u = {{32{instr[31]}}, instr[31:12], 12'b0};
Pułapka LUI w RV64 LUI w RV32 robi imm << 12 do 32 bitów. W RV64 wynik jest sign-extendowany do 64 bitów — więc lui x4, 0x80001 daje 0xFFFFFFFF80001000, nie 0x0000000080001000. Właśnie dlatego w testach używamy auipc + addi zamiast lui do ładowania adresów powyżej 0x8000_0000.

Pipeline Core

To top-level rdzenia. Zawiera 5 stopni, 4 rejestry pipeline (IF/ID, ID/EX, EX/MEM, MEM/WB), jednostkę forwardingu i detektor hazardów. Poniżej pełna struktura. 

module rv64i_pipe_core (
    input  wire        clk, rst,
    output wire [63:0] imem_addr,
    input  wire [31:0] imem_data,
    output wire [63:0] dmem_addr, dmem_wdata,
    output wire        dmem_we, dmem_re,
    output wire [1:0]  dmem_size,
    input  wire [63:0] dmem_rdata,
    output reg         halted,
    output wire [63:0] dbg_pc
);
    // IF stage
    reg  [63:0] pc;
    wire [31:0] if_instr = imem_data;
    assign imem_addr = pc;

    // IF/ID register
    reg [63:0] ifid_pc;
    reg [31:0] ifid_instr;
    reg        ifid_valid;

    // ID stage → decoder instance
    // EX stage → ALU + forwarding + branch resolution
    // MEM stage → memory access
    // WB stage → writeback to regfile
    // ...
endmodule

Pamięć

Moduł rv64i_mem symuluje pamięć harwardzką: osobno instrukcje (32-bit words) i dane (64-bit words). Zawiera też detekcję zapisu do tohost pod adresem 0x8000_1000 — to standardowy mechanizm komunikacji z testbenchem (protokół riscv-tests). 

module rv64i_mem #(
    parameter MEM_WORDS = 32768,
    parameter BASE      = 64'h0000_0000_8000_0000
)(
    // instruction port
    input  wire [63:0] iaddr,
    output wire [31:0] idata,
    // data port
    input  wire [63:0] daddr, dwdata,
    input  wire        dwe, dre,
    input  wire [1:0]  dsize,
    output wire [63:0] drdata,
    // tohost interface
    output reg         tohost_we,
    output reg  [63:0] tohost_data
);
    reg [31:0] imem [0:MEM_WORDS-1];
    reg [63:0] dmem [0:MEM_WORDS-1];
    reg [1023:0] hexpath;

    initial begin
        if ($value$plusargs("HEX=%s", hexpath))
            $readmemh(hexpath, imem);
    end
    // ...
endmodule
Konwencja tohost Program zapisuje 1 pod 0x8000_1000 = PASS. Wartość > 1 to numer failującego testu. To standard przyjęty w riscv-tests i riscv-arch-test — jeśli nasz rdzeń to obsługuje, będzie kompatybilny z oficjalnymi zestawami testów.

Pipeline szczegółowo

Klasyczny 5-stopniowy potok RISC. Każdy stopień robi jedną rzecz i przekazuje wynik do następnego przez rejestr pipeline. W jednym cyklu zegara 5 instrukcji jest na różnych etapach zaawansowania.

1IFFetch — pobierz instrukcję z I-mem
→
2IDDecode — zdekoduj, odczytaj rejestry
→
3EXExecute — ALU, branch, CSR
→
4MEMMemory — load/store
→
5WBWriteback — zapis do regfile

IF — Instruction Fetch

Stopień IF pobiera 32-bitową instrukcję z pamięci pod adresem pc. W tym samym cyklu oblicza się pc + 4 jako domyślny następny PC. 

reg  [63:0] pc;
wire [31:0] if_instr = imem_data;
assign imem_addr = pc;

always @(posedge clk) begin
    if (ex_redirect)       pc <= ex_redirect_target;
    else if (!stall)        pc <= pc + 64'd4;
end

Dwie rzeczy mogą zmienić PC:

  • Redirect — branch wzięty, JAL/JALR, trap, mret
  • Stall — load-use hazard, wtedy PC stoi

ID — Instruction Decode

Dekoder zamienia 32-bitową instrukcję na sygnały sterujące. Jednocześnie register file odczytuje rs1 i rs2. Wyniki lądują w rejestrze IF/ID → ID/EX. 

always @(posedge clk) begin
    if (flush || stall) begin
        // bubble — wyzeruj wszystkie sygnały kontrolne
        idex_reg_we <= 1'b0;
        idex_mem_re <= 1'b0;
        idex_mem_we <= 1'b0;
        // ...
    end else begin
        idex_pc      <= ifid_pc;
        idex_rs1_val <= id_rs1_val;
        idex_rs2_val <= id_rs2_val;
        idex_imm     <= id_imm;
        idex_alu_op  <= id_alu_op;
        // ...
    end
end

EX — Execute

Stopień EX robi najwięcej: ALU, rozwiązywanie branchy, dostęp do CSR-ów, detekcja trapów. Tutaj też działa forwarding — dane z EX/MEM i MEM/WB mogą być użyte zamiast odczytu z regfile.

Forwarding (priorytet EX/MEM > MEM/WB > regfile)

wire fwd_a_exmem = exmem_reg_we && (exmem_rd != 5'd0) && (exmem_rd == idex_rs1);
wire fwd_b_exmem = exmem_reg_we && (exmem_rd != 5'd0) && (exmem_rd == idex_rs2);
wire fwd_a_memwb = memwb_reg_we && (memwb_rd != 5'd0) && (memwb_rd == idex_rs1) && !fwd_a_exmem;
wire fwd_b_memwb = memwb_reg_we && (memwb_rd != 5'd0) && (memwb_rd == idex_rs2) && !fwd_b_exmem;

wire [63:0] ex_rs1 = fwd_a_exmem ? exmem_alu_y : fwd_a_memwb ? wb_wdata : idex_rs1_val;
wire [63:0] ex_rs2 = fwd_b_exmem ? exmem_alu_y : fwd_b_memwb ? wb_wdata : idex_rs2_val;

Rozwiązywanie branchy

always @(*) begin
    case (idex_branch_op)
        3'b001: ex_branch_taken = (ex_rs1 == ex_rs2);              // BEQ
        3'b010: ex_branch_taken = (ex_rs1 != ex_rs2);              // BNE
        3'b011: ex_branch_taken = ($signed(ex_rs1) < $signed(ex_rs2)); // BLT
        3'b100: ex_branch_taken = ($signed(ex_rs1) >= $signed(ex_rs2)); // BGE
        3'b101: ex_branch_taken = (ex_rs1 < ex_rs2);              // BLTU
        3'b110: ex_branch_taken = (ex_rs1 >= ex_rs2);             // BGEU
        default:ex_branch_taken = 1'b0;
    endcase
end
Branch penalty = 2 cykle Branch rozwiązywany w EX oznacza, że 2 instrukcje pobrane po branchu (w IF i ID) są błędne i trzeba je wyrzucić (flush). To jest koszt 2 cykli na każdy wzięty branch. Produkcyjne rdzenie rozwiązują branch wcześniej (w ID) albo stosują predykcję skoków, żeby zredukować ten koszt.

MEM — Memory

Dostęp do pamięci danych. Tylko instrukcje load/store tu robią cokolwiek — dla pozostałych to jest "przepuszczanie" wyniku ALU. 

assign dmem_addr  = exmem_alu_y;
assign dmem_wdata = exmem_rs2_val;
assign dmem_we    = exmem_mem_we;
assign dmem_re    = exmem_mem_re;
assign dmem_size  = exmem_mem_size;

WB — Writeback

Zapis wyniku do register file. Wynik może pochodzić z trzech źródeł:

  • ALU — dla operacji arytmetycznych
  • Pamięć — dla load (z sign/zero extension)
  • CSR — dla instrukcji CSR
assign wb_wdata = memwb_is_csr ? memwb_csr_rdata :
                  memwb_mem_re ? wb_load_ext : memwb_alu_y;
assign wb_we    = memwb_reg_we;
assign wb_rd    = memwb_rd;

Hazardy i Forwarding

RAW (Read After Write) — hazard danych

Najczęstszy hazard: instrukcja chce odczytać rejestr, który jeszcze nie został zapisany przez poprzednią instrukcję (bo jest w EX/MEM, a nie w WB). 

# Przykład RAW
add  x1, x2, x3   # x1 gotowe po WB
add  x4, x1, x5   # ale potrzebne już w EX → forwarding!

Rozwiązanie: forwarding (data bypass). Wynik z EX/MEM lub MEM/WB jest podawany bezpośrednio do wejścia ALU, zamiast czekać na WB.

Load-use hazard

Specjalny przypadek: instrukcja load ma wynik dopiero po MEM, więc nawet forwarding nie wystarcza. Trzeba zatrzymać pipeline na 1 cykl (wstawić bubble). 

# Load-use — wymaga stall
ld   x1, 0(x2)     # load
add  x3, x1, x4    # używa x1 — musi poczekać 1 cykl
wire load_use_hazard =
    idex_mem_re && (idex_rd != 5'd0) && ifid_valid &&
    ((idex_rd == id_rs1) || (idex_rd == id_rs2));

wire stall = load_use_hazard;
Stall = bubble w EX Kiedy stall=1, rejestr ID/EX zapisuje bubble (wszystkie sygnały kontrolne na 0). To gwarantuje, że EX wykona NOP-a zamiast drugi raz tej samej instrukcji.

Control hazard

Branch rozwiązywany w EX, więc instrukcje pobrane w IF i ID (po branchu) są błędne jeśli branch wzięty. Trzeba je wyrzucić (flush) — wyzerować ifid_valid i sygnały kontrolne w ID/EX. 

wire ex_redirect = ex_trap_take || ex_mret_take
                   || idex_is_jump || (idex_is_branch && ex_branch_taken);
wire flush = ex_redirect;

Write-first regfile — 3-instr gap

Standardowe forwarding pokrywa luki 1 i 2 instrukcji. Luka 3 instrukcji (np. divuw → lui → addi → bne) wymaga write-first regfile albo 3. poziomu forwardingu. 

assign rdata1 = (rs1 == 5'd0) ? 64'd0 :
                (we && rd == rs1) ? wdata : regs[rs1];

CSR i trapy — praktyka

Schemat obsługi trapa w RISC-V jest zunifikowany — wszystkie wyjątki przechodzą przez ten sam mechanizm:

  1. Procesor zapisuje mepc ← aktualne PC
  2. Zapisuje mcause ← kod przyczyny
  3. Zapisuje mtval ← dodatkowa informacja (np. kod instrukcji)
  4. Ustawia mstatus.MPIE ← mstatus.MIE, MIE ← 0
  5. Skacze do mtvec (adres handlera)

Powrót przez mret:

  1. mstatus.MIE ← mstatus.MPIE
  2. mstatus.MPIE ← 1
  3. PC ← mepc

Przykład — handler ecall

handler:
    addi a0, a0, 1        # inkrementuj licznik
    csrr t0, mepc
    addi t0, t0, 4        # pomiń ecall (PC += 4)
    csrw mepc, t0
    mret                  # powrót
Test trap.S — PASS Test weryfikuje: CSR read/write round-trip (mscratch), ecall → handler → mret, oraz sprawdzenie mcause = 11 po powrocie. Wszystkie warunki przeszły na RTL.

Workflow — od asemblera do symulacji

Ścieżka od źródła .S do działającego testu na RTL: 

┌──────────────────────────────────────────────────────────────┐
│  1. test.S         (źródło asemblera RISC-V)                 │
│       ↓ riscv64-linux-gnu-gcc -march=rv64im_zicsr ...        │
│  2. test.elf       (ELF z symbolami)                         │
│       ↓ riscv64-linux-gnu-objcopy -O binary                  │
│  3. test.bin       (raw binarka, little-endian)              │
│       ↓ xxd -p -c4 / python3 (byte-swap)                     │
│  4. test.hex       (32-bit hex words, jeden na linię)        │
│       ↓ Verilator + $readmemh                                │
│  5. obj_dir/Vtb_rv64i_pipe                                   │
│       ↓ +HEX=test.hex                                        │
│  6. [tohost] value=0x...  →  PASS/FAIL                       │
└──────────────────────────────────────────────────────────────┘

Flagi GCC — dlaczego każda jest potrzebna

FlagaCel

Pułapka — la generuje GOT access Bez -fno-pic -mcmodel=medany + .hidden tohost, pseudo-instrukcja la t0, tohost wygeneruje dostęp przez GOT (auipc + ld), a GOT w binarce bez relokacji jest śmieciem. Prowadzi to do cichego timeoutu. Widzieliśmy to — t0 dostawał 0 zamiast 0x80001000.

Konwersja bin → hex (byte-swap)

RISC-V w pamięci jest little-endian, ale $readmemh czyta słowa 32-bitowe. Trzeba zamienić 13 05 50 00 (4 bajty) na 00500513 (jedno 32-bit słowo). 

python3 - "$BASE.bin" > "$BASE.hex" <<'PY'
import sys
d = open(sys.argv[1],'rb').read()
while len(d) % 4: d += b'\x00'
for i in range(0, len(d), 4):
    print(f'{int.from_bytes(d[i:i+4], "little"):08x}')
PY

Docelowa architektura

Celem jest rdzeń zgodny z platformą QEMU -M virt, co pozwoli uruchomić ten sam OS na:

  • QEMU — szybkie prototypowanie (na x86_64)
  • Własnym RTL — symulacja Verilator
  • FPGA — rzeczywisty hardware (Artix-7 / ECP5)
  • Silicon — jeśli kiedyś dojdzie do tape-outu

Klucz: identyczne adresy peryferiów. UART @ 0x1000_0000, CLINT @ 0x0200_0000, PLIC @ 0x0C00_0000 — dokładnie jak w QEMU virt. Wtedy uart_putc w OS działa bez zmian na wszystkich platformach.

# 1. Uruchom na QEMU, zapisz trace

# 3. Diff
