1. Introduction: The Bootstrapping Problem

The Chicken-and-Egg Dilemma: To manage memory dynamically, an operating system needs data structures (like linked lists or trees). But to create those data structures, it needs to allocate memory. How do you allocate memory before you have a memory allocator?

CoTanOS solves this through a layered, phased approach. We start with the simplest, dumbest, but most reliable allocator possible. Once that is running, we use it to build a slightly smarter allocator, and so on, until we have a production-grade, SMP-safe, fragmentation-resistant memory management subsystem.

2. The Memory Hierarchy (The Big Picture)

The CoTanOS memory subsystem is divided into four distinct layers, each building upon the previous one:

  1. Arena Early Boot: A simple "bump" allocator. It only moves forward. Used to allocate the metadata for the next layers.
  2. Frame Physical Pages: Manages raw RAM in fixed-size chunks (4KB, 2MB, 1GB). Uses a highly optimized bitmap.
  3. Zone Hardware Constraints: Groups physical frames into zones (DMA, DMA32, Normal) based on hardware addressing limits.
  4. Slab Kernel Objects: Carves frames into fixed-size object caches (e.g., 64-byte task structs) to eliminate fragmentation and provide O(1) allocation speed.

3. Layer 1: Early Boot Arena (arn.rs)

Analogy: Imagine a roll of tape. You pull out what you need, cut it, and the next person pulls from where you left off. You can't put tape back on the roll, but it's incredibly fast and requires no complex bookkeeping.

The ArenaAllocator is the very first allocator initialized. The bootloader (UEFI/BIOS) hands the kernel a block of usable RAM. The arena simply hands out slices of this block.

Key Architectural Features:

  • Lock-Free & SMP-Safe: Uses AtomicUsize with Acquire/Release memory ordering. Multiple CPU cores can wake up and allocate from the arena simultaneously without traditional locks, preventing boot-time deadlocks.
  • Cache-Line Isolation: The struct is marked with #[repr(C, align(64))]. This ensures the atomic offset counter sits alone in its CPU cache line, preventing false sharing (where multiple cores fighting over adjacent variables slow down the whole memory bus).
  • Null-Page Guard: If the bootloader provides memory starting at physical address 0x0, the arena automatically skips it. In Rust, a null pointer is Undefined Behavior (UB). This guard prevents the creation of invalid NonNull pointers.
  • Zero-Sized Type (ZST) Handling: Requesting 0 bytes doesn't consume arena space; it returns a safely aligned "dangling" pointer, preventing pointer aliasing bugs.

4. Layer 2: Physical Frame Allocator (frm.rs & map.rs)

What is a Frame? Operating systems don't manage memory byte-by-byte; that would require terabytes of metadata. Instead, memory is divided into fixed-size blocks called frames (or pages), typically 4 Kilobytes (4KB), 2 Megabytes (2MB), or 1 Gigabyte (1GB).

The Frame Allocator tracks which frames are free and which are in use. CoTanOS uses a Bitmap approach, managed by the BitmapLayout engine.

How the Bitmap Engine Works:

  • Word-Oriented Scanning: The bitmap is stored as an array of 64-bit integers (&mut [u64]). Instead of checking 64 individual bits one by one, the allocator checks the whole 64-bit word at once. If the word is 0xFFFF_FFFF_FFFF_FFFF, it knows all 64 frames are allocated and skips them instantly. This makes scanning blazingly fast.
  • Contiguous Allocation: Devices like network cards (DMA) often need a block of physically adjacent frames. The bitmap engine features a sliding-window algorithm to find N consecutive free frames efficiently.
  • Padding Protection: If the total number of frames isn't a perfect multiple of 64, the "extra" bits at the end of the last word are permanently marked as allocated (1). This prevents the allocator from ever handing out memory that doesn't exist.

SMP & Interrupt Safety (IrqSpinlock):

The Deadlock Scenario: CPU 1 holds the frame allocator lock. An hardware interrupt occurs on CPU 1. The interrupt handler also needs a frame. It tries to acquire the lock... and the system freezes forever.

CoTanOS solves this with IrqSpinlock. When a core acquires this lock, it first disables local hardware interrupts. This guarantees that an interrupt handler on the same core cannot preempt the code and cause a deadlock. The previous interrupt state is saved and perfectly restored when the lock is dropped.

5. Layer 3: Zone Manager (zon.rs)

Analogy: Imagine a parking garage. Some spots are for compact cars only (low clearance), some for standard cars, and some for trucks. You wouldn't put a compact car in a truck spot if you can avoid it, and a truck physically cannot fit in a compact spot.

Not all hardware can address all memory. A legacy ISA device might only have 24 address lines, meaning it physically cannot see any memory above 16 Megabytes. The Zone Manager partitions physical memory to respect these hardware limits.

The Zones:

  • DMA Zone: Physical addresses below 16 MiB. For legacy hardware.
  • DMA32 Zone: Physical addresses below 4 GiB. For modern 32-bit PCI devices.
  • Normal Zone: All remaining memory above 4 GiB. General-purpose kernel use.
  • HighMem Zone: Memory above the kernel's direct-mapping window (architecture-dependent).

Intelligent Fallback:

If a driver requests memory from the DMA32 zone, but it is completely full, the Zone Manager doesn't immediately panic with an Out-Of-Memory (OOM) error. Instead, it intelligently falls back to the Normal zone (if the hardware supports it via IOMMU, or as a last resort), ensuring system stability.

6. Layer 4: Slab Allocator (slb.rs)

The Fragmentation Problem: If you constantly allocate and free random sizes (e.g., 45 bytes, then 112 bytes), physical memory becomes like "Swiss cheese." You might have 100MB of total free memory, but no single contiguous 50MB block. This is external fragmentation.

The Slab Allocator eliminates external fragmentation by grouping kernel objects into fixed-size caches (e.g., 32B, 64B, 128B, up to 8KB). When you ask for 45 bytes, it gives you a 64-byte slot.

How a Slab Cache Works:

  1. The allocator requests a 4KB frame from the Frame Allocator.
  2. It divides this frame into, for example, sixty-four 64-byte objects.
  3. It links all free objects together into a singly linked free list embedded directly inside the unused memory of the objects themselves (zero metadata overhead!).
  4. Allocation is now O(1): just pop the first item off the free list. Deallocation is O(1): just push it back on.

Production-Grade Debugging Features:

When compiled with debug_assertions, the slab allocator becomes a powerful bug-hunting tool:

  • Redzones: It allocates extra bytes before and after the object, filling them with a specific pattern (0xAD). If a buffer overflow occurs, it overwrites this pattern. Upon deallocation, the allocator checks the redzones and instantly panics with a "Redzone Corruption" error, pinpointing the exact bug.
  • Poisoning: When an object is freed, its memory is filled with a poison pattern (0xDE). If the kernel accidentally tries to read from this freed memory (Use-After-Free), it will read garbage data, making the bug obvious rather than silently corrupting state.

7. Observability: Statistics & Diagnostics (stat.rs)

A kernel is only as good as its ability to be debugged. The stat module provides a unified, lock-free way to query the health of all allocators.

  • Lock-Free Counters: Uses AtomicU64 to track allocation/deallocation counts and byte totals. This adds near-zero overhead to the hot allocation path.
  • Fragmentation Index: Calculates a score from 0.0 (perfect, all free memory is contiguous) to 1.0 (fully fragmented, memory is in tiny, unusable holes). This is critical for long-running systems.
  • Kernel Shell Integration: Provides fmt::Display implementations so memory reports can be easily printed to a serial console or kernel shell via a simple meminfo command.

    8. Safety & Correctness Guarantees

    CoTanOS memory management is written in Rust, leveraging the compiler to eliminate entire classes of bugs. Key guarantees include:

    • #![no_std] Purity: The crate has zero dependencies on the Rust standard library. No hidden heap allocations, no floating-point operations (safe for early boot before FPU initialization).
    • Checked Arithmetic: Every addition, subtraction, or multiplication involving memory addresses or sizes uses .checked_add() or .saturating_sub(). Integer overflows return Result::Err or None, they never silently wrap around and corrupt memory.
    • Strict unsafe Boundaries: The crate uses #![deny(unsafe_op_in_unsafe_fn)]. This means even inside an unsafe fn, every single dereference of a raw pointer or call to an unsafe intrinsic must be wrapped in its own explicit unsafe { ... } block. This forces the developer to consciously acknowledge and justify every single unsafe operation.
    • Lifetime Enforcement: Methods like alloc_slice<'a>(&'a self) tie the returned memory directly to the lifetime of the allocator. The Rust compiler will statically prevent you from using arena-allocated memory after the arena has been reset or dropped.
